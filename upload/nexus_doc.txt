1. Executive Overview
1.1 Purpose of This Document
This document serves as the authoritative technical specification for the NEXUS Multi-Agent LLM Orchestration Harness. It provides a comprehensive, implementation-ready description of every major subsystem, integration surface, configuration surface, and operational protocol that constitutes the NEXUS platform. The specification covers the complete system architecture, from the top-level orchestration engine down to individual agent system prompts, model adapter interfaces, and MCP server protocols. This document is intended to be the single source of truth for all engineering decisions related to the NEXUS codebase.
NEXUS is designed to address a fundamental gap in the current AI tooling landscape: the absence of a production-grade, provider-agnostic orchestration layer that can coordinate multiple specialized LLM agents through structured debate, tool use, and consensus protocols. While frameworks such as LangChain, AutoGen, and CrewAI provide multi-agent primitives, they often lack the deep integration with development environments, the rigorous debate mechanics, and the security-first architecture that NEXUS delivers out of the box.
The specification covers two primary distribution targets: a VS Code Extension that integrates directly into the world's most popular code editor, and a standalone Desktop Application built with Tauri (Rust shell with web frontend) that can operate independently of any IDE. Both targets share a common core library, ensuring feature parity and consistent behavior across deployment surfaces.

This document is written for a technical audience with backgrounds in software engineering, artificial intelligence, and systems architecture. The primary readers include:

2. System Architecture Overview
2.1 High-Level Architecture Description
NEXUS is architected as a three-layer system that cleanly separates concerns between the hosting environment, the connectivity infrastructure, and the agent coordination logic. This separation ensures that the same orchestration core can be embedded in a VS Code Extension, a standalone desktop application, or even a headless server process, without requiring modifications to the core agent logic.
The highest layer, the Host Layer, encompasses the user-facing application shell. In the VS Code Extension context, this includes the Webview panel, Activity Bar integration, Command Palette actions, and Language Model API hooks. In the Desktop Application context, this includes the Tauri window management, the Next.js/React frontend, and the system tray integration. The Host Layer is responsible for rendering the UI, capturing user intent, and presenting results, but it delegates all orchestration work to the layers below.
The middle layer, the Connectivity Layer, manages all communication with external services. This includes the Universal Model Gateway (which normalizes API calls across dozens of LLM providers), the MCP Host (which manages connections to MCP servers for tool execution), the Secret Manager (which handles credential storage and retrieval), and the Telemetry Collector (which aggregates observability data). The Connectivity Layer is designed to be independently testable through dependency injection and mock adapters.
The lowest layer, the Coordination Layer, implements the core intelligence of the system. This includes the Orchestrator (which manages the task DAG and agent scheduling), the Debate Engine (which mediates structured disagreements between agents), the Agent Runtime (which manages agent lifecycles and context windows), and the Memory System (which provides persistent state, vector search, and cross-session recall). The Coordination Layer is the heart of NEXUS and is the primary focus of this specification.
2.2 Three-Layer Architecture
The three-layer architecture follows strict dependency direction: the Host Layer depends on the Connectivity Layer, which in turn depends on the Coordination Layer. The Coordination Layer has zero dependencies on the upper layers, making it portable and testable in isolation. This inversion-of-control pattern is enforced through TypeScript interfaces and dependency injection containers.

2.3 Key Design Principles
Provider-Agnostic: NEXUS does not mandate any specific LLM provider. Every agent can be configured to use any provider supported by the Model Gateway, including cloud APIs (OpenAI, Anthropic, Google, Mistral, Groq, Together, Azure, Bedrock) and local runtimes (Ollama, LM Studio, vLLM, llama.cpp, KoboldCPP). This allows teams to mix and match providers based on cost, latency, capability, and data sovereignty requirements.
MCP-First: All tool use, file system access, and external service integration is mediated through the Model Context Protocol. NEXUS does not implement custom tool-calling abstractions; instead, it acts as an MCP Host that discovers, configures, and invokes tools from MCP Servers. This ensures interoperability with the growing MCP ecosystem and allows organizations to bring their own tool servers.
Security-by-Default: No agent has unrestricted access to any tool or resource. The permission model requires explicit consent for destructive operations, enforces allow/deny lists, and provides backup plans when tool access is denied. All credential access goes through the Secret Manager rather than passing API keys in plaintext.
Deterministic Outputs: The debate protocol, task decomposition, and consensus mechanism are designed to produce reproducible results given the same inputs and configuration. Random tie-breaking is avoided in favor of structured arbitration rules. Session transcripts are stored in full for audit and replay.
Debate-Then-Decide: Rather than trusting a single LLM's output, NEXUS routes every non-trivial task through a structured debate between at least two agents with different system prompts and, ideally, different underlying models. This adversarial approach catches errors, security vulnerabilities, and design flaws that a single-model approach would miss.
2.4 Component Interaction Flow
A typical NEXUS session proceeds through the following flow: (1) The user submits a task through the Host Layer UI, which is parsed into a structured TaskRequest object. (2) The Orchestrator receives the TaskRequest, invokes the ARCHITECT agent to decompose it into a Directed Acyclic Graph (DAG) of subtasks, and schedules execution. (3) For each subtask, the Orchestrator selects the appropriate agent(s), provides context from the Memory System, and initiates execution. (4) If the subtask involves code generation, the output is routed to the SENTINEL agent for adversarial review. (5) If ARCHITECT and SENTINEL disagree, the Debate Engine is invoked to mediate a structured critique-and-rebuttal cycle. (6) Once consensus is reached, the output is committed to the task state and the next subtask begins. (7) Upon completion, the SCRIBE agent generates a summary, changelog, or PR description. (8) The user is presented with the final result through the Host Layer.
2.5 Monorepo Structure Overview
The NEXUS codebase is organized as a monorepo with the following top-level directories: /core (shared libraries for model gateway, MCP host, orchestrator, memory, security, and telemetry), /clients/vscode-extension (the VS Code Extension target), /clients/desktop-app (the Tauri desktop application), /clients/cli (optional headless CLI interface), /servers (built-in MCP servers for filesystem, git, terminal, browser, OCR, vision, audio, vectorstore, testrunner, and linter), /docs (this documentation and API references), and /tests (unit, integration, and evaluation tests). The monorepo uses pnpm workspaces with TypeScript project references for type-safe cross-package imports.
3. Agent Roster & Specializations
3.1 Introduction to the Agent Council
NEXUS employs a council of five specialized agents, each with a distinct system prompt, personality, and area of expertise. This multi-agent approach is inspired by research in multi-agent debate (Du et al., 2023) and mixture-of-agents (Wang et al., 2024), which demonstrates that aggregating outputs from diverse LLMs produces superior results compared to any single model. The council is not democratic; the ARCHITECT agent serves as the final arbiter, but it must engage with and respond to the arguments of other agents before rendering a decision.
Each agent is defined as a configuration object that specifies its role, system prompt template, preferred model providers, tool access permissions, context window budget, and cost ceiling. This configuration-driven approach allows operators to customize agent behaviors without modifying the core codebase, and even to add entirely new agent roles to the council.
3.2 Agent 1: ARCHITECT (Planner/Orchestrator)
The ARCHITECT is the senior agent in the NEXUS council, responsible for task decomposition, planning, and final arbitration of debates. It receives the user's high-level task description and produces a structured DAG of subtasks, assigning each subtask to the most appropriate agent. During debates, the ARCHITECT serves as the judge, weighing the arguments of FORGE and SENTINEL and rendering a final verdict. The ARCHITECT must be a model with strong reasoning and planning capabilities; recommended models include Claude 3.5 Sonnet/Opus, GPT-4o, or Gemini 1.5 Pro. Local alternatives include Llama 3.1 70B or DeepSeek Coder V2.
3.3 Agent 2: FORGE (Primary Coder)
FORGE is the primary code generation agent. It receives subtasks from the ARCHITECT and produces implementation code, architecture decisions, and technical solutions. FORGE is optimized for code quality, correctness, and adherence to best practices. It has access to the full suite of development tools via MCP (filesystem, git, terminal, linter) and can execute code in the sandbox. Recommended models include Claude 3.5 Sonnet (best-in-class for code), GPT-4o, or DeepSeek Coder V2. The key requirement is strong code generation capability, not necessarily strong reasoning or planning.
3.4 Agent 3: SENTINEL (Secondary Coder / Adversarial Reviewer)
SENTINEL plays a critical adversarial role in the NEXUS council. Rather than generating original code, SENTINEL reviews FORGE's output with the explicit goal of finding flaws: bugs, security vulnerabilities, performance issues, architectural inconsistencies, and deviations from requirements. SENTINEL operates under a system prompt that instructs it to be skeptical, thorough, and uncompromising. The diversity principle requires that SENTINEL uses a different model family than FORGE (e.g., if FORGE uses Claude, SENTINEL should use GPT-4o or Gemini). This model diversity ensures that correlated model biases are caught by the adversarial review.
3.5 Agent 4: PERCEPTION (Tool/Multimodal Specialist)
PERCEPTION is the MCP tool specialist and multimodal I/O agent. It owns all interactions with external tools and data sources, including OCR (extracting text from images), computer vision (analyzing screenshots and UI mockups), audio transcription, web browsing, and database queries. PERCEPTION serves as the bridge between the LLM reasoning of other agents and the messy reality of external data. It is configured to use models with strong multimodal capabilities, such as GPT-4o (vision), Claude 3.5 Sonnet (vision), or Gemini 1.5 Pro (native multimodal).
3.6 Agent 5: SCRIBE (Docs/Comms Agent)
SCRIBE handles all documentation and communication tasks. It generates changelogs, PR descriptions, commit messages, inline code comments, README updates, and user-facing summaries. SCRIBE is configured to use a cost-effective model, as documentation tasks rarely require frontier-level intelligence. Recommended models include Claude 3 Haiku, GPT-4o-mini, or locally-hosted Llama 3.1 8B. The cost optimization principle ensures that expensive models are reserved for agents that genuinely need them.

4. Master Orchestrator System Prompt
4.1 System Identity and Role Definition
The master orchestrator prompt defines the system-level identity and behavioral constraints for the NEXUS coordination engine. This prompt is injected at the top of every agent's context window, establishing the shared communication protocol, operating principles, and escalation procedures that govern inter-agent interaction. The master prompt is immutable during a session and cannot be modified by any agent.
The master prompt establishes NEXUS as a multi-agent orchestration system, not a chatbot. It explicitly instructs agents that they are participating in a structured workflow, that their outputs will be reviewed by other agents, and that they must produce structured, machine-parseable responses rather than conversational prose. This framing is critical for eliciting the focused, task-oriented behavior that makes multi-agent orchestration effective.

4.3 Operating Principles
Structured Output First: All agent responses must be valid JSON unless explicitly instructed otherwise by the task specification. Free-form text is only acceptable in designated 'reasoning' or 'explanation' fields within the structured output.
Context Window Discipline: Each agent must manage its context window budget carefully. When approaching the limit, agents should summarize prior context rather than allowing the window to fill with raw conversation history.
Tool Use Transparency: Every tool invocation must be logged with its inputs, outputs, and duration. Agents must not silently invoke tools without including the invocation in their response.
Graceful Degradation: If a required tool is unavailable, an agent must describe what it attempted, why it failed, and propose an alternative approach rather than failing silently or producing an incomplete result.
4.4 Agent Coordination Rules
The coordination rules establish precedence and authority within the agent council. The ARCHITECT has final authority on task decomposition and debate arbitration. FORGE has authority over implementation decisions within its assigned subtasks. SENTINEL has authority to block any output that fails its review, triggering a mandatory debate cycle. PERCEPTION has authority over all tool invocations and data interpretation. SCRIBE has authority over all outbound documentation and communication. No agent may override another agent's primary domain without initiating a formal debate.
5. Individual Agent System Prompts
5.1 ARCHITECT Agent Prompt
The ARCHITECT's system prompt establishes it as the senior planning agent with primary responsibility for understanding the user's intent, decomposing complex tasks into executable subtasks, assigning subtasks to appropriate agents, and arbitrating debates when agents disagree. The prompt instructs the ARCHITECT to think in terms of dependency graphs, to identify parallelizable work, and to minimize the total number of agent turns required to complete a task. The ARCHITECT is explicitly told that its planning quality directly affects the quality of the final output, and that it should invest sufficient reasoning effort in the planning phase before delegating work.
The ARCHITECT prompt includes specific instructions for debate arbitration: when FORGE and SENTINEL disagree, the ARCHITECT must (1) read both arguments in full, (2) identify the specific points of disagreement, (3) evaluate each argument against the original requirements, (4) consider edge cases and failure modes raised by either side, and (5) render a clear verdict with justification. The ARCHITECT is prohibited from simply agreeing with the most recent argument or defaulting to either agent.
5.2 FORGE Agent Prompt
The FORGE prompt establishes it as the primary implementation agent. FORGE is instructed to produce clean, well-documented, production-quality code that follows the project's established patterns and conventions. The prompt emphasizes correctness over cleverness, readability over brevity, and robustness over performance (unless performance is an explicit requirement). FORGE is told that its output will be reviewed by SENTINEL and that it should anticipate common criticisms: missing error handling, insufficient test coverage, hardcoded values, security anti-patterns, and deviations from the ARCHITECT's plan.
FORGE's prompt includes specific coding standards: all functions must have explicit return types, all public APIs must have JSDoc/TSDoc documentation, all error paths must be handled explicitly, and all external dependencies must be declared in the appropriate manifest file. FORGE is also instructed to produce a brief self-review of its own code before submission, identifying any areas of uncertainty or potential improvement.
5.3 SENTINEL Agent Prompt
The SENTINEL prompt is explicitly adversarial. It instructs the agent to review submitted work with maximum skepticism, adopting the persona of a senior security engineer and code reviewer who has seen countless bugs slip through into production. The prompt tells SENTINEL to look for: logic errors and off-by-one mistakes, injection vulnerabilities (SQL, XSS, command injection), insecure defaults and hardcoded secrets, missing input validation, race conditions and concurrency bugs, incorrect error handling that swallows exceptions, performance bottlenecks and N+1 query patterns, and deviations from the task specification.
Critically, the SENTINEL prompt instructs the agent to provide constructive feedback rather than simply rejecting work. Every criticism must include a specific location (file and line), a clear explanation of the issue, a concrete suggestion for remediation, and a severity rating (critical, major, minor, suggestion). This structured feedback format enables the Debate Engine to efficiently process disagreements and identify the core issues.
5.4 PERCEPTION Agent Prompt
The PERCEPTION prompt establishes the agent as the gateway to all external tools and multimodal inputs. PERCEPTION is responsible for invoking MCP tools, interpreting their results, extracting structured data from unstructured sources (OCR, audio transcription, web scraping), and presenting the processed information to other agents in a consumable format. The prompt emphasizes accuracy in data extraction, appropriate handling of ambiguous inputs, and clear documentation of any transformations applied to the raw data.
PERCEPTION's tool access is the broadest of any agent: it can invoke filesystem operations, execute terminal commands (within the sandbox), navigate web pages, process images and audio, and query databases. However, this broad access comes with strict safety constraints: all terminal commands are executed in a sandboxed container, all filesystem writes require explicit confirmation, and all network access is logged and rate-limited.
5.5 SCRIBE Agent Prompt
The SCRIBE prompt establishes the agent as the documentation and communication specialist. SCRIBE receives the completed work from other agents and produces: changelog entries in Keep a Changelog format, pull request descriptions with clear summaries of changes, inline code comments for complex logic, README updates reflecting new features, and user-facing summaries of what was accomplished. The prompt instructs SCRIBE to match the tone and style of existing documentation, to use active voice, and to avoid unnecessary jargon. SCRIBE is also responsible for generating the final session summary that is presented to the user at the end of a NEXUS task.
6. Debate & Consensus Protocol
6.1 Overview and Purpose
The Debate Protocol is the cornerstone of NEXUS's quality assurance mechanism. Rather than relying on a single LLM's output, NEXUS routes every non-trivial code submission through a structured debate between the FORGE (author) and SENTINEL (reviewer) agents, with the ARCHITECT serving as the final arbiter. This adversarial process is inspired by research demonstrating that multi-agent debate significantly improves factual accuracy, reduces hallucination, and catches errors that a single-model approach would miss (Du et al., 2023).
The protocol is designed to be efficient: most debates resolve within a single critique-rebuttal cycle, and the ARCHITECT can short-circuit the debate if the SENTINEL raises only minor issues. The protocol also includes configurable escalation thresholds: if the debate exceeds a maximum number of rounds without reaching consensus, the task is escalated to human-in-the-loop review, preventing infinite debate loops.
6.2 Protocol Phases
The debate protocol proceeds through six well-defined phases:
DRAFT: The FORGE agent produces its implementation and submits it to the debate engine. The submission includes the code, rationale, and a self-assessment of potential issues.
CRITIQUE: The SENTINEL agent reviews FORGE's submission and produces a structured critique. The critique includes specific findings with severity ratings and remediation suggestions.
REBUTTAL: FORGE responds to SENTINEL's critique, either accepting the feedback and revising the code, or defending its original implementation with counterarguments.
ARBITRATE: The ARCHITECT reviews both the critique and the rebuttal, identifies the core points of disagreement, and renders a verdict. The verdict includes a clear decision on each contested point.
VERIFY: The accepted solution is subjected to automated verification: linting, type checking, unit tests, and any other validation steps specified in the task configuration.
COMMIT: Once verified, the solution is committed to the task state and the orchestrator proceeds to the next subtask.

6.5 Maximum Debate Rounds and Escalation
The debate protocol includes a configurable maximum number of rounds to prevent indefinite deliberation. The default is three rounds for Council Mode and five rounds for Red Team Mode. If the debate exceeds this threshold without reaching consensus, the system automatically escalates to human-in-the-loop review. The escalation creates a user-facing notification that includes the full debate transcript, a summary of the unresolved points, and options to (a) accept the current version, (b) accept SENTINEL's suggested changes, (c) restart the debate with a different model configuration, or (d) manually edit the code.
The escalation mechanism is a critical safety feature: it ensures that the system never gets stuck in an infinite loop of agent disagreement, and that the human operator retains ultimate authority over the codebase. Escalation statistics are tracked as a telemetry signal; high escalation rates may indicate a need for better model configuration or more precise task specification.
6.6 Debate Transcript Storage and UI Visualization
Every debate session produces a full transcript that is stored in the session database. The transcript includes: the original submission, all critique and rebuttal exchanges, the ARCHITECT's arbitration, the verification results, and the final commit decision. Transcripts are stored in a structured format that enables efficient querying, filtering, and replay. The VS Code Extension and Desktop Application both include a Debate Log tab that renders the transcript as a visual timeline, with color-coded severity ratings, expandable code diffs, and one-click navigation to the affected source locations.
7. MCP (Model Context Protocol) Integration
7.1 MCP Architecture Overview
The Model Context Protocol (MCP) is an open standard that provides a universal way for LLM applications to connect to external tools and data sources. NEXUS implements the MCP Host role, which means it manages the lifecycle of MCP Client connections, each of which communicates with one or more MCP Servers. This architecture enables NEXUS to discover, configure, and invoke tools from any MCP-compliant server, whether built-in or provided by third parties.
The MCP architecture follows a three-party model: the Host (NEXUS), which orchestrates the overall session and provides the user interface; one or more Clients, each maintaining a persistent connection to a specific MCP Server; and the Servers, which expose tools, resources, and prompts through a standardized JSON-RPC interface. This separation allows a single Host to aggregate capabilities from multiple Servers simultaneously, creating a rich tool ecosystem for agents.
7.2 Transport Mechanisms
MCP supports three transport mechanisms, each suited to different deployment scenarios:
• stdio transport: The MCP Server runs as a child process of the MCP Client, communicating via stdin/stdout. This is the simplest and most secure transport, ideal for local tools that run on the same machine as the Host.
• SSE (Server-Sent Events) transport: The MCP Server runs as an HTTP server, and the Client connects via a long-lived SSE connection. This supports remote servers and enables the Server to push notifications to the Client.
• Streamable HTTP transport: An evolution of SSE that supports bidirectional streaming, request cancellation, and multiplexed message channels. This is the preferred transport for production deployments and cloud-hosted MCP servers.
7.3 Tool Discovery Protocol
MCP follows a three-step discovery and invocation protocol:
• initialize: The Client sends an initialize request to the Server, exchanging capabilities and negotiating protocol version. The Server responds with its capabilities, including supported tools, resources, and prompt templates.
• tools/list: After initialization, the Client requests the Server's tool manifest. The Server responds with a list of tool definitions, each including a name, description, and JSON Schema for the input parameters.
• tools/call: When an agent needs to invoke a tool, the Client sends a tools/call request with the tool name and parameters. The Server executes the tool and returns the result, which is passed back to the requesting agent.

7.6 Tool Permission Model and Safety Constraints
NEXUS implements a layered tool permission model that ensures agents cannot perform unauthorized or destructive actions. The model has three tiers: (1) Allow List: tools that an agent can invoke without explicit permission for each call (e.g., filesystem:read for PERCEPTION). (2) Consent List: tools that require user confirmation before each invocation (e.g., terminal:exec, filesystem:write). (3) Deny List: tools that an agent is explicitly prohibited from invoking (e.g., ARCHITECT cannot use terminal:exec). The permission model is configurable per-agent in the agent role configuration, and it includes a default-deny policy for any tool not explicitly listed.

8. Universal Model Gateway (Provider Adapter Layer)
8.1 Design Requirements and IModelAdapter Interface
The Universal Model Gateway is the abstraction layer that allows NEXUS to communicate with any LLM provider through a single, unified interface. The gateway is designed around the IModelAdapter interface, which defines the contract that all provider-specific adapters must implement. This interface specifies methods for: chat completion (with support for tool calling), streaming responses, token counting, model listing, and health checking. The interface is intentionally provider-agnostic; it does not expose any provider-specific features (e.g., Anthropic's thinking mode or OpenAI's response format) through the main interface, though adapters can expose provider-specific options through an optional extension mechanism.
The IModelAdapter interface is defined in TypeScript as follows: the adapter must implement completeChat(request) which returns a normalized ChatResponse, streamChat(request) which returns an async iterable of ChatChunk events, countTokens(text, model) which returns an estimated token count, listModels() which returns available model identifiers, and checkHealth() which returns a boolean indicating whether the provider endpoint is reachable and responsive.
8.2 Cloud API Adapters
NEXUS provides first-class adapters for the following cloud LLM providers, each implementing the IModelAdapter interface with provider-specific optimizations:
• OpenAI: Supports GPT-4o, GPT-4o-mini, o1, o3, and all OpenAI models. Implements function calling via the tools parameter. Supports structured outputs with response_format.
• Anthropic: Supports Claude 3.5 Sonnet, Claude 3.5 Haiku, Claude 3 Opus, and all Anthropic models. Implements tool use via the tools parameter. Supports extended thinking and prompt caching.
• Google Gemini: Supports Gemini 1.5 Pro, Gemini 1.5 Flash, and Gemini 2.0 models. Implements function calling via functionDeclarations. Supports native multimodal input.
• Mistral: Supports Mistral Large, Mistral Medium, Mistral Small, Codestral, and Pixtral. Implements function calling and JSON mode.
• Groq: Ultra-low-latency inference for Llama 3.1, Mixtral, and other open models. Ideal for agents that require fast response times.
• Together AI: Supports a wide range of open-source models with competitive pricing. Useful for cost-sensitive deployments.
• Azure OpenAI: Enterprise-grade OpenAI deployment with VNet integration, private endpoints, and compliance certifications.
• AWS Bedrock: Enterprise-grade Anthropic, Meta, and Cohere model access with IAM authentication and VPC isolation.
8.3 Local Runtime Adapters
NEXUS provides adapters for the most popular local LLM runtimes, enabling fully offline operation:
• Ollama (localhost:11434): The most popular local LLM runtime. Supports automatic model pulling from Ollama Hub. Adapter implements the Ollama REST API, including streaming and tool calling support.
• LM Studio (localhost:1234): A user-friendly local LLM GUI that exposes an OpenAI-compatible REST API. The LM Studio adapter reuses the OpenAI adapter with a custom base URL.
• vLLM (localhost:8000): A high-performance inference server optimized for throughput. Ideal for serving large models on multi-GPU setups. Supports OpenAI-compatible API.
• llama.cpp (localhost:8080): The reference C/C++ inference engine for GGUF-quantized models. Supports CPU and GPU inference with minimal dependencies.
• KoboldCPP (localhost:5001): A lightweight inference server optimized for consumer hardware. Supports GPU offloading and quantized models.
8.4 Custom Endpoint Support
Any endpoint that implements the OpenAI-compatible REST API can be connected to NEXUS as a custom provider. This includes self-hosted inference servers (vLLM, TGI, Triton), cloud GPU providers (RunPod, Modal, Replicate), and enterprise inference gateways. The custom endpoint adapter accepts a base URL, API key, and optional model mapping configuration. The adapter validates the endpoint's health and tool-calling support during initialization.
8.5 Auto-Discovery of Local Endpoints
On startup, NEXUS probes common local ports (11434, 1234, 8000, 8080, 5001) to detect running LLM servers. When a server is detected, NEXUS queries its /v1/models endpoint to discover available models and automatically adds them to the model registry. This zero-configuration discovery means that users can start Ollama or LM Studio and immediately use those models in NEXUS without any manual configuration. Discovered models are listed in the Model Gateway panel with a 'local' badge.
8.6 Response Normalization
Every adapter normalizes its provider-specific response format into a unified ToolCall schema. This schema represents tool calls as objects with name, arguments (a JSON object), and id fields, regardless of whether the underlying provider uses OpenAI's function calling, Anthropic's tool_use, or Gemini's functionCall format. This normalization is critical for the orchestrator, which must be able to process tool calls uniformly regardless of which provider generated them. The normalization layer also handles edge cases such as parallel tool calls, partial tool calls in streaming mode, and tool call refusals.
8.7 Secret Management
API keys and other credentials are never stored in plaintext configuration files. NEXUS integrates with the OS keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service) via the VS Code SecretStorage API in the extension context, and via the keyring library in the desktop application context. Credentials are referenced in configuration by a secure URI scheme: secrets://provider/api-key. The Secret Manager resolves these URIs at runtime, ensuring that secrets are only ever present in memory and never written to disk.
8.8 Token and Cost Accounting
The Model Gateway tracks token usage for every API call, disaggregated by agent, session, and provider. Costs are calculated in real-time using provider-specific pricing tables that are updated regularly. The cost accounting system enforces per-agent and per-session budget ceilings, automatically switching to cheaper models or pausing execution when a budget is exhausted. Cost data is displayed in the Cost/Usage panel and exported as structured telemetry for integration with billing and analytics systems.
8.9 Fallback Chains
Each agent can be configured with a fallback chain: an ordered list of model providers to try if the primary provider fails or returns an error. For example, the ARCHITECT might be configured with: primary: anthropic/claude-3.5-sonnet, fallback-1: openai/gpt-4o, fallback-2: google/gemini-1.5-pro, fallback-3: ollama/llama-3.1-70b. The fallback mechanism handles rate limits (HTTP 429), service outages (HTTP 503), context window overflow, and content filter rejections. Each fallback is logged with the reason for the fallback and the alternative provider used.
9. VS Code Extension Architecture
9.1 Extension Overview and Key Features
The NEXUS VS Code Extension brings the full power of the multi-agent orchestration system directly into the developer's IDE. The extension is built on the VS Code Extension API and provides a rich panel-based interface for interacting with agents, monitoring debates, configuring models, and reviewing results. The extension is the primary distribution target for individual developers and small teams who want to integrate AI-powered code generation and review into their existing VS Code workflows.
Key features include: multi-agent chat with structured debate visualization, agent roster management with per-agent model configuration, real-time task DAG visualization showing the progress of complex multi-step tasks, a debate log with color-coded findings and severity ratings, a model gateway panel showing provider status, available models, and cost tracking, an MCP server management panel for configuring tool servers, and a cost/usage dashboard with per-session and per-agent breakdowns.
9.2 Activity Bar Panel: NEXUS Council
The extension adds a dedicated NEXUS Council panel to the Activity Bar (left sidebar). This panel contains seven tabs, each providing a focused view into a different aspect of the system. The Chat tab provides a conversational interface for submitting tasks and viewing results. The Agent Roster tab displays the configured agents with their current status, model assignments, and tool permissions. The Task DAG tab visualizes the current task's execution graph with real-time progress indicators. The Debate Log tab shows the history of all debates with expandable details. The Model Gateway tab shows provider status, model availability, and cost tracking. The MCP Servers tab lists configured MCP servers with their connection status and available tools. The Cost/Usage tab provides detailed cost breakdowns and budget utilization charts.
9.3 Inline Features
Beyond the panel interface, the extension provides several inline features that integrate directly into the code editing experience. CodeLens actions appear above function definitions, allowing developers to request agent actions (e.g., 'Generate tests,' 'Review code,' 'Optimize') without leaving the editor. A diff view integration shows the agent's proposed changes alongside the original code, with one-click accept/reject controls. Problems panel integration surfaces agent-identified issues (linting errors, security warnings, type errors) directly in VS Code's standard Problems panel. The status bar shows the current session status, active agent, and cost accumulator.
9.4 Implementation Details
The extension is implemented in TypeScript and follows VS Code extension best practices. The UI is rendered in a Webview using React, communicating with the extension host via VS Code's Webview API (postMessage). The extension integrates with VS Code's Language Model API (vscode.lm) for providers that support it, falling back to direct API calls for providers that do not. Secret Storage is used for all credential management, ensuring that API keys are stored securely in VS Code's encrypted storage.
9.5 Command Palette Actions

9.6 Packaging and Publishing
The extension is packaged as a standard VSIX file and published to both the VS Code Marketplace and Open VSX Registry. The packaging pipeline uses vsce for Marketplace publishing and ovsx for Open VSX. The extension supports VS Code version 1.85.0 and later, and is tested on Windows, macOS, and Linux. The extension uses VS Code's proposed APIs (guarded by capability checks) for features that require newer VS Code versions, with graceful fallbacks for older versions.
10. Standalone Desktop Application Architecture
10.1 Architecture: Local-First, Single Binary
The NEXUS Desktop Application is a local-first application that can operate entirely offline (with local models) or connect to cloud LLM providers for enhanced capabilities. The application is distributed as a single binary that bundles the backend server, the frontend assets, and the built-in MCP servers. This single-binary distribution eliminates complex installation procedures and ensures consistent behavior across platforms. The application supports Windows (NSIS installer and portable), macOS (DMG with universal binary), and Linux (AppImage, DEB, RPM).
10.2 Backend: FastAPI or NestJS
The desktop application's backend can be implemented in either Python (FastAPI) or Node.js (NestJS), depending on the deployment team's expertise. The Python/FastAPI backend is recommended for teams that prioritize ecosystem integration (e.g., scientific computing, data analysis workflows), while the Node.js/NestJS backend is recommended for teams that want maximum code sharing with the shared core library (which is written in TypeScript). Both backends expose the same REST API surface and WebSocket endpoints, and both implement the same plugin interface for extensibility.
10.3 Frontend: Tauri with React/Next.js
The desktop application's frontend is built with Tauri, which provides a Rust-based shell with a webview renderer. The webview hosts a React/Next.js application that shares significant UI code with the VS Code Extension's Webview. Tauri was chosen over Electron for its significantly smaller binary size (approximately 10MB vs 100MB+), lower memory footprint, and better native platform integration. The Rust shell handles native OS operations such as filesystem access, system tray management, and auto-updates, while the webview handles the rich, interactive UI.
10.4 Task Orchestration Engine
The desktop application's Task Orchestration Engine is a DAG executor that manages the execution of complex, multi-step tasks. The engine supports: parallel execution of independent branches, sequential execution of dependent subtasks, conditional branching based on intermediate results, retry with exponential backoff for transient failures, human-approval gates that pause execution until the user confirms, and timeout enforcement per subtask. The engine maintains a persistent task state that survives application restarts, enabling long-running tasks to resume after interruption.
10.5 Event Bus and Persistence
An internal event bus provides real-time updates to the UI. Every significant event (agent turn, tool invocation, debate phase transition, cost threshold breach) is published to the event bus, which the frontend subscribes to via WebSocket. This ensures that the UI always reflects the current state of the orchestration engine without polling. Persistence is handled by SQLite for single-user deployments and PostgreSQL for team/server deployments. A vector database (Qdrant or ChromaDB) provides embedding storage for the memory system's RAG capabilities.
10.6 Sandbox and Deployment Targets
Code execution in the desktop application occurs within a Docker container or OS-level sandbox (e.g., Firejail on Linux, sandbox-exec on macOS, Windows Sandbox). The sandbox provides filesystem isolation, network isolation (configurable), resource limits (CPU, memory, disk), and automatic cleanup after execution. The desktop application supports three deployment targets: local desktop (default, single-user), self-hosted Docker Compose (multi-user, shared database), and cloud SaaS (managed deployment with OAuth/SSO authentication and horizontal scaling).
11. Shared Core Architecture
11.1 Core Module Layout
The /core directory contains the shared libraries that power both the VS Code Extension and the Desktop Application. These modules are organized into six packages, each with clear responsibility boundaries and well-defined public APIs:
• core/model-gateway: The Universal Model Gateway, including the IModelAdapter interface, all provider adapters, the fallback chain engine, and the token/cost accounting system.
• core/mcp-host: The MCP Host implementation, including client lifecycle management, transport abstraction, tool discovery, and the permission enforcement engine.
• core/orchestrator: The orchestration engine, including the DAG executor, agent scheduling, debate protocol, and consensus resolution logic.
• core/memory: The memory system, including conversation history management, vector search for RAG, cross-session recall, and context window budget management.
• core/security: The security module, including sandbox management, secret resolution, audit logging, and the tool permission engine.
• core/telemetry: The observability module, including OpenTelemetry instrumentation, structured logging, session replay, and export to external observability tools.
11.2 Client Wrappers
The /clients directory contains the target-specific wrappers that adapt the shared core to each deployment surface. The vscode-extension client wraps the core in the VS Code Extension API, providing Webview hosting, SecretStorage integration, LanguageModel API hooks, and the Activity Bar panel UI. The desktop-app client wraps the core in a Tauri application, providing the system tray, native window management, Docker sandbox integration, and the full-screen desktop UI. The optional cli client provides a headless interface for CI/CD integration and batch processing.
11.3 Cross-Cutting Requirements
Observability: Every module emits structured events through the telemetry module, enabling end-to-end tracing of agent turns, tool calls, and debate rounds.
Deterministic Replay: Every session can be replayed from its stored transcript, given the same model providers and configuration. This enables debugging, evaluation, and regression testing of agent behaviors.
Configuration-as-Code: All behavioral parameters (model selection, debate thresholds, permission policies, budget ceilings) are expressed in version-controlled configuration files rather than UI toggles.
Plugin SDK: A TypeScript SDK for developing custom agents, MCP servers, and provider adapters that integrate with the NEXUS core through well-defined extension points.
12. Security Model & Threat Mitigation
12.1 Threat Model Overview
NEXUS operates in a high-threat environment by design: it executes code, invokes external tools, manages secrets, and communicates with remote API endpoints on behalf of AI agents. The threat model identifies four primary attack vectors: prompt injection (an adversary manipulates agent behavior through carefully crafted inputs), remote code execution via tool calls (an agent or injected prompt causes the terminal MCP server to execute malicious commands), secret exfiltration (an agent or tool returns data that includes API keys, credentials, or other secrets), and supply chain attacks (compromised MCP servers or model providers inject malicious behavior).
12.2 Sandboxed Execution Model
All code execution occurs within an isolated sandbox environment. The sandbox is implemented as a Docker container with the following constraints: no network access by default (network access can be enabled per-task with explicit approval), read-only filesystem with a writable temporary directory, CPU and memory limits enforced by Docker cgroups, and automatic destruction after task completion. The sandbox runs as an unprivileged user with no access to the host's Docker socket, keychain, or environment variables. Secrets are injected into the sandbox only when explicitly required by the task, and are revoked immediately after use.
12.3 Secret Management Architecture
Secrets are stored in the OS keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service) and are never written to disk in plaintext. The Secret Manager provides a secure resolution service: agents and tools reference secrets by URI (secrets://provider/api-key), and the Secret Manager resolves these URIs at runtime. The Secret Manager enforces the principle of least privilege: each agent receives only the secrets it needs for its assigned tools, and secrets are scoped to the duration of a single tool invocation. Audit logs record every secret access event, including the requesting agent, the tool name, and the timestamp.
12.4 Tool Permission Model
The tool permission model implements defense-in-depth through three layers: (1) Agent-level allow/deny lists define which tools each agent can potentially invoke. (2) Tool-level consent requirements specify which tools require explicit user confirmation before execution. (3) Backup plans define alternative actions when a tool is unavailable or denied. For example, if FORGE attempts to execute a terminal command but the user denies consent, the backup plan specifies that FORGE should describe the command it intended to run and ask the user to execute it manually. This ensures that workflow progress is never permanently blocked by a permission denial.
12.5 Audit Logging Requirements
Every significant action in NEXUS is recorded in an immutable audit log. The audit log captures: agent invocations (who, when, what model, what prompt), tool invocations (who, what tool, what inputs, what outputs, duration), debate events (phase transitions, verdicts, escalation triggers), permission decisions (granted, denied, escalated, and the rationale), and secret access events (who accessed what secret and when). Audit logs are stored in a tamper-evident format (append-only with cryptographic hashes) and can be exported for compliance review.
12.6 Security-by-Default Principles
• No secrets in config files: All credentials are stored in the OS keychain, never in YAML or JSON configuration.
• No unrestricted tool access: Every tool requires explicit permission; the default is deny.
• No direct network access from agents: All network requests go through the MCP Host with configurable allow/deny lists.
• No persistent sandbox state: Sandbox containers are destroyed after each use, preventing persistent compromise.
• Full audit trail: Every action is logged, and logs are tamper-evident.
13. Observability & Telemetry
13.1 OpenTelemetry Integration
NEXUS integrates with OpenTelemetry to provide comprehensive, vendor-neutral observability. Every significant operation in the system is instrumented as a span: agent turns (with attributes for agent ID, model, token count, and duration), tool calls (with attributes for tool name, input parameters, output size, and duration), debate rounds (with attributes for phase, verdict, and number of findings), model gateway calls (with attributes for provider, model, status code, and latency), and MCP client operations (with attributes for server, transport, and message type). Spans are propagated across process boundaries using W3C Trace Context, enabling end-to-end tracing from user request to final output.
13.2 Token Tracking and Cost Accounting
The telemetry module tracks token consumption at multiple granularities: per-agent-turn, per-task, per-session, and per-calendar-period. Token counts are recorded for both input (prompt) and output (completion) tokens, disaggregated by provider. Costs are calculated using a configurable pricing table that supports tiered pricing, volume discounts, and currency conversion. Budget alerts are triggered when cumulative cost exceeds configurable thresholds (e.g., 50%, 75%, 90%, 100% of the session budget). The cost accounting data is exposed through the UI's Cost/Usage panel and is exported as structured telemetry for integration with external billing and analytics systems.
13.3 Session Replay Capability
Every NEXUS session produces a complete, ordered transcript that captures every agent turn, tool invocation, debate exchange, and user interaction. This transcript is stored in the session database and can be replayed in the UI to reproduce the exact sequence of events. Session replay is invaluable for debugging agent behaviors, evaluating model performance, and training new team members on the system's capabilities. The replay functionality supports variable-speed playback and branching (forking a session from any point to explore alternative agent decisions).
13.4 Export to Observability Tools
NEXUS supports export to several popular observability platforms: Langfuse for LLM-specific tracing and evaluation, Phoenix (Arize) for LLM observability and performance monitoring, custom dashboards via Prometheus metrics and Grafana visualization, and generic OpenTelemetry exporters for any OTLP-compatible backend. Export is configured through the telemetry section of nexus.config.yaml and supports both push (OTLP exporter) and pull (Prometheus endpoint) modes.
13.5 Structured Logging
All logging in NEXUS is structured JSON logging with consistent field names. Log entries include: timestamp (ISO 8601), level (debug, info, warn, error), component (model-gateway, orchestrator, mcp-host, etc.), session_id, agent_id (when applicable), event_type, and a context object with event-specific fields. Structured logging enables efficient searching, filtering, and aggregation using tools such as jq, Grafana Loki, or Elasticsearch. Log levels are configurable per-component, allowing verbose logging for specific subsystems during debugging without flooding the logs with noise from other components.
14. Testing Strategy
14.1 Unit Tests for Core Orchestration
The core orchestration modules (DAG executor, debate engine, agent scheduler, memory manager) are covered by comprehensive unit tests. Unit tests use mocked IModelAdapter and IMCPServer interfaces to isolate the logic under test from external dependencies. Tests cover: task decomposition and DAG construction, agent scheduling and parallel execution, debate phase transitions and arbitration logic, context window management and summarization, fallback chain resolution, permission evaluation, and token budget enforcement. The target coverage for core modules is 80% or higher, measured by line coverage with strict branch coverage for the debate engine.
14.2 Integration Tests for Provider Adapters
Provider adapter integration tests verify that each adapter correctly implements the IModelAdapter interface and handles edge cases. Tests use recorded HTTP responses (VCR-style fixtures) rather than live API calls, ensuring repeatability and avoiding API cost. Test cases cover: successful chat completion with various model configurations, streaming response handling, tool call normalization across provider formats, error handling (rate limits, server errors, invalid requests), token counting accuracy, and health check behavior. New adapters are required to pass the full adapter test suite before being merged.
14.3 Agent Evaluation Harness
Beyond traditional software testing, NEXUS includes an agent evaluation harness that measures the quality of agent outputs on standardized benchmarks. The evaluation harness runs a suite of coding tasks (from HumanEval, MBPP, and custom benchmarks) through the full NEXUS pipeline and measures: task success rate (does the final output pass all tests?), debate quality (does the SENTINEL catch real bugs without raising false positives?), code quality (linting score, type safety, documentation coverage), and efficiency (number of agent turns, total tokens consumed, wall-clock time). Evaluation results are tracked over time to detect regressions and measure the impact of model upgrades or prompt changes.
14.4 Extension Smoke Tests
The VS Code Extension includes automated smoke tests that verify basic functionality: extension activation, panel rendering, model gateway connectivity, MCP server startup, and chat submission. These tests run in VS Code's Extension Development Host and are executed as part of the CI pipeline on every pull request. The desktop application includes equivalent smoke tests that verify Tauri window creation, backend server startup, and WebSocket connectivity.
14.5 CI Pipeline Requirements
The CI pipeline runs on every pull request and includes: linting (ESLint with strict rules), type checking (TypeScript with strict mode), unit tests (Vitest), integration tests (Vitest with mocked providers), agent evaluation (subset of benchmarks), extension smoke tests, and build verification (VSIX packaging and Tauri build). The pipeline is configured to fail if any test fails, if code coverage drops below the 80% threshold, or if the build produces errors. Nightly runs execute the full evaluation benchmark suite and produce a comparison report against the previous run.
15. Build Plan (Phase-by-Phase Implementation)
15.1 Overview
The NEXUS build plan is organized into ten phases, each delivering a self-contained increment of functionality. Each phase is designed to be completable within a focused sprint (2-4 weeks) and produces a testable, demonstrable artifact. The phases are ordered to maximize early learning: the Model Gateway and MCP Host are built first because they validate the most critical external integrations, while the UI shells are built later because they depend on the core functionality.

15.2 Phase 0: Repository Scaffold
Phase 0 establishes the monorepo structure, development tooling, and CI pipeline. This includes: initializing the pnpm workspace with TypeScript project references, configuring ESLint with strict rules and Prettier for formatting, setting up Vitest for unit and integration testing, configuring GitHub Actions for CI (lint, type-check, test, build), establishing the /core, /clients, /servers, /docs, and /tests directory structure, and creating the nexus.config.yaml schema and validation logic. Phase 0 produces a green CI pipeline and a validated repository structure that all subsequent phases build upon.
15.3 Phase 1: Model Gateway
Phase 1 implements the Universal Model Gateway and three initial adapters: OpenAI, Anthropic, and Ollama. This phase validates the IModelAdapter interface design and establishes the patterns that all subsequent adapters will follow. Key deliverables include: the IModelAdapter TypeScript interface with JSDoc documentation, the response normalization layer that unifies tool call formats, the fallback chain engine, the token counting and cost accounting system, and comprehensive integration tests with VCR-style HTTP fixtures. The OpenAI and Anthropic adapters exercise the full feature set (streaming, tool calling, structured output), while the Ollama adapter validates the local runtime discovery pattern.
15.4 Phase 2: MCP Host and Single-Agent Execution
Phase 2 implements the MCP Host and three essential MCP servers (filesystem, git, terminal), enabling single-agent execution. This phase delivers the first end-to-end capability: a user can submit a task, a single agent (FORGE) can plan and execute it using MCP tools, and the results are presented to the user. Key deliverables include: the MCP Host with stdio transport, the three MCP servers with tool discovery and invocation, a basic chat interface for submitting tasks and viewing results, and the agent runtime that manages context windows and tool invocations.
15.5 Phase 3 through Phase 9
Phases 3 through 9 progressively build out the full NEXUS capability set. Phase 3 adds the Orchestrator DAG engine and the ARCHITECT agent, enabling multi-step planning and task decomposition. Phase 4 adds the SENTINEL agent and the full Debate Protocol, enabling adversarial review and consensus-based quality assurance. Phase 5 adds the PERCEPTION agent and multimodal MCP servers (OCR, vision, audio), enabling rich input processing. Phase 6 wraps the core in a VS Code Extension shell with the full panel-based UI. Phase 7 creates the Tauri desktop application with a full-screen UI. Phase 8 adds observability, cost tracking, and Docker sandboxing for production readiness. Phase 9 delivers the Plugin SDK, marketplace listings, documentation site, and automated release pipeline.
16. Configuration Reference
16.1 nexus.config.yaml Schema
The primary configuration file for NEXUS is nexus.config.yaml, which is typically located in the project root. This file controls all behavioral parameters: agent roster, model assignments, MCP server connections, security policies, and observability settings. The configuration is validated against a JSON Schema at startup, and invalid configurations produce clear error messages.

16.2 Agent Role Configuration JSON
Each agent role can also be specified as a standalone JSON file, which is useful for sharing agent configurations across projects or version-controlling agent personas. The JSON schema includes fields for the agent's identity (id, name, description), system prompt (as a file reference or inline string), model configuration (primary, fallback, parameters), tool permissions (allow/deny lists with glob patterns), budget constraints (cost and token limits), and behavioral overrides (temperature, top_p, presence_penalty, frequency_penalty).
16.3 MCP Server Configuration
MCP servers are configured in the mcpServers section of nexus.config.yaml. Each server configuration specifies: the transport type (stdio, sse, or streamable-http), the command to start the server (for stdio transport) or URL to connect to (for SSE/HTTP), command-line arguments, environment variables (with secret URI support), auto-start behavior, tool-level permission overrides, and health check configuration. Servers can be enabled or disabled without removing their configuration, making it easy to temporarily disable a server for testing.
16.4 Provider Adapter Configuration
Provider adapters are configured in the modelGateway.providers section. Each provider configuration specifies: the base URL for API requests, the API key (resolved via secrets:// URI), optional headers, default model parameters (temperature, max_tokens, etc.), rate limit configuration, and retry policy. Custom providers that implement the OpenAI-compatible API can be added under a custom provider name with the openAiCompatible flag set to true, which causes NEXUS to use the OpenAI adapter with the custom base URL.
17. Counterarguments & Limitations
17.1 Complexity Overhead vs Single-Model Approaches
The most significant criticism of the NEXUS approach is its complexity relative to single-model approaches. A system that uses a single LLM with function calling can achieve many of the same tasks with far less infrastructure: no multi-agent coordination, no debate protocol, no agent roster management, and no consensus resolution. For simple tasks (code completion, single-file refactoring, documentation generation), a single-model approach is likely more efficient in terms of latency, cost, and engineering effort. NEXUS's multi-agent approach is justified when task complexity exceeds a threshold where the marginal quality improvement of adversarial review outweighs the marginal cost of additional agent turns.
The recommended threshold is: use NEXUS for any task that (a) spans multiple files or subsystems, (b) requires architectural decisions with trade-offs, (c) has security implications, or (d) will be reviewed by other humans. For simpler tasks, NEXUS should be configured in Fast Mode (single-pass review) or the user should use a direct chat interface.
17.2 Latency Implications of Multi-Agent Debate
Multi-agent debate introduces significant latency compared to single-model approaches. A typical Council Mode debate involves three sequential LLM calls (FORGE draft, SENTINEL critique, ARCHITECT arbitration), each taking 5-15 seconds for complex tasks. This means a full debate cycle adds 15-45 seconds of latency on top of the original code generation time. For interactive workflows where developers expect sub-second feedback, this latency is unacceptable. NEXUS mitigates this by: (1) making debate optional for simple tasks, (2) streaming intermediate results to the UI so the developer can see progress, (3) supporting parallel execution of independent subtasks, and (4) caching repeated patterns to avoid redundant agent turns.
17.3 Cost Considerations
Multi-agent orchestration consumes significantly more tokens (and thus costs more) than single-model approaches. A single NEXUS task might involve 5-15 LLM calls across multiple agents, compared to 1-3 calls in a single-model workflow. With frontier models pricing at $5-15 per million input tokens and $15-75 per million output tokens, a complex NEXUS session can cost $0.50-5.00. NEXUS mitigates cost through: per-agent budget ceilings that prevent runaway spending, intelligent model routing (using cheap models for simple agents like SCRIBE), local model support for cost-free execution, and detailed cost tracking that enables users to make informed trade-offs.
17.4 Model Diversity and Correlated Failure Modes
The adversarial review model assumes that FORGE and SENTINEL use different models, which provides diversity of perspective. However, if both models are fine-tuned from the same base or trained on similar data, they may exhibit correlated failure modes: both missing the same type of bug, both making the same incorrect assumption, or both generating the same anti-pattern. This correlation undermines the value of adversarial review. NEXUS mitigates this by: (1) requiring different model families for FORGE and SENTINEL in the default configuration, (2) providing guidance on model diversity in the configuration documentation, and (3) including a diagnostic that detects when FORGE and SENTINEL agree too frequently (which may indicate insufficient model diversity).
17.5 Local Model Limitations for Agent Roles
While NEXUS supports local models via Ollama, LM Studio, vLLM, and llama.cpp, local models have significant limitations compared to frontier cloud models. Local models typically have smaller context windows (8K-32K vs 128K-200K for cloud models), lower instruction-following accuracy, weaker tool-calling reliability, and limited multimodal capabilities. This means that fully offline NEXUS operation, while possible, will produce lower-quality results than cloud-connected operation. The recommended approach is a hybrid: use frontier cloud models for critical roles (ARCHITECT, FORGE, SENTINEL) and local models for ancillary roles (SCRIBE, PERCEPTION for simple tasks).
17.6 Alternative Approaches
Several alternative approaches exist in the multi-agent orchestration space. OpenAI Swarm provides lightweight, stateless multi-agent coordination but lacks structured debate and security features. Microsoft AutoGen offers sophisticated conversation patterns but requires significant Python expertise and lacks IDE integration. CrewAI provides role-based agent orchestration but is primarily Python-based and does not support MCP. LangGraph offers graph-based workflow orchestration but requires manual graph construction and does not include built-in adversarial review. NEXUS differentiates from these alternatives by providing: MCP-native tool integration, structured debate with configurable modes, both VS Code and desktop deployment targets, TypeScript core with Python/Node.js backend options, and security-by-default architecture.
17.7 Mitigations and Recommended Thresholds
To maximize the value of NEXUS while managing its overhead, the following thresholds are recommended: use Fast Mode for tasks estimated at under 5 minutes of work; use Council Mode for tasks spanning multiple files or involving architectural decisions; use Red Team Mode only for security-critical code (authentication, authorization, cryptography, payment processing); set per-session cost budgets based on task value (e.g., $0.10 for a simple refactor, $1.00 for a feature implementation, $5.00 for a system-level change); and monitor escalation rates, targeting below 10% (higher rates indicate model configuration or task specification issues).
